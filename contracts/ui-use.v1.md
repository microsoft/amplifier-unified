# UI-use host integration v1

The portable UI-use behavior owns the bounded controller and selection policy; provider modules own decision inference and authentication. Unified supplies optional target discovery, managed-browser lifetime, device delivery, presentation and user preferences. Canonical computer-use owns desktop observation and input.

A host registers `ui.use.host` as an async callable accepting an operation and JSON arguments. Browser requests use open/observe/act/targets, with optional explicit target. Results retain domain status and exact target identity. Selection configuration is resolved per call. The host may expose preferences, status and a viewer to any authenticated client. Tool calls never receive owner credentials or device tokens.

Explicit task target and active session target take precedence over chat, workspace and global preferences; the final default is an isolated managed browser. A chosen connected device never silently switches to a different account or machine. Unavailable targets return a recovery choice. Failure after possible input is unknown and never replayed. Stop stays latched until the user resumes.

When the selected computer-use bundle exposes episode ownership, the native adapter sponsors the entire computer UI-use invocation, including selection and independent final verification. Direct desktop calls retain a lazy episode through their actual native generation, not chat selection or model prose. Finite child completion and persistent-child turn completion are distinct boundaries. Stop fences local admission before serialized controls and retains asynchronous native settlement. A cancelled awaiter, successful task, or confirmed input release does not by itself prove the indicator settled; the bundle owns those separate facts. Explicit Resume clears only the host's UI latch, never an old episode or the bundle's durable halt. Missing lifecycle support preserves explicitly selected older bundles without claiming episode qualification.

Normal disclosure/readiness follows the bundle's own wait policy, not the shorter cleanup wait; Stop/cancellation wakes the caller without cancelling or losing an in-flight acquisition. A completed begin refusal retires only a synthetic obligation when the controller proves no episode was acquired, including after retiring a fully settled previous episode; ambiguous startup or transport loss stays unresolved. Episode settlement waits in ordinary tool completion and close are bounded. Expiry of that wait reports unconfirmed/stopping custody, never a release acknowledgement or a replacement child execution result/error/cancellation: the exact controller, generation and native cleanup obligation remain retained, new desktop acquisition/retarget is refused, and passive status can reconcile recovery. Child cleanup reports are explicitly cleanup-scoped, excluding unrelated normal activity without claiming whole-computer release. Worker replacement and child backend cleanup do not replace unresolved custody, and bounded child-row eviction cannot remove a cleanup admission barrier. Idle workers retain their native writer; retirement requires confirmed episode settlement and rechecks pending work after its awaited checkpoint. Shutdown retains its cleanup owner through the existing host's exact-process Stop/escalation boundary; process death is not native input-release or indicator-settlement proof. Unchanged unknown status is not repeatedly published.

Decision inference is optional. Explicit ordinary selection wins; otherwise a configured, enabled decision backend is preferred with ordinary selection on unavailable, uncertain or ineffective decisions. No implicit credential discovery activates a backend. Provider state disclosure consent remains authoritative. Selection progress identifies the actual backend and fallback.

Installed provider-owned decision catalogs may declare `decision_only` and `connection` setup hints (authentication, endpoint, description). Clients offer these as optional connections without inventing chat models or probing a nonexistent chat catalog. Saving a connection does not activate inference or claim a successful live check. Surface selection is a separate explicit setting; credentials remain in the existing provider configuration. Local inference services must be installed and reachable separately.

Browser and computer selections are independent and can both be configured. `providers.configureDecisions` accepts `purpose: both` to save the same choice for both in one transaction, retaining separate backend identities. Both bindings and account configuration must be effective in the explicitly selected scope; a narrower conflicting override rejects the entire save. Choosing one purpose later preserves the other. Installation alone never selects a provider, and clients must offer connection setup separately from installation rather than treating an update check as account setup.

Decision-only accounts use real hook modules shipped by their existing provider packages. The module-authored catalog may declare `runtime: {kind: hook, module: hooks-…}`; it supplies no independent source or credentials. A mixed provider may additionally declare the single supported condition `when: {chat_enabled: false}`. Ordinary chat-plus-decision accounts retain the normal provider lifecycle. This composition requires no capability-only exception in Core.

Worker catalog discovery runs in a bounded helper process without passed account configuration or credential environment, and returns only validated hook metadata. Discovery must not import an installed provider into the execution process before its exact configured source is prepared. The result, including discovery failure, is fixed for that worker's immutable dependency generation; unknown discovery results cannot authorize a mount.

Unified prepares and validates the logical saved account before projecting it into a hook at the same effective source. Conflicting hook sources, duplicate identities and unauthorized inherited bindings fail before use. Projection metadata is transient: configuration presentation, persistence and child/resume binding restore logical provider rows and redact credentials. A hook envelope cannot authorize another account, source or credential. Disabled decision-only accounts remain saved but are omitted from runtime mounts; package installation and ambient keys do not activate them.

Each projected mount reports an exact account lifecycle receipt through a private host callback. Only complete rollback permits an unavailable outcome and the configured ordinary fallback. Missing, invalid, cancelled or unsafe receipts prevent initialization; unrelated hook failures remain fatal. Failed decision accounts never become chat fallback providers. The hook owns partial-registration cleanup, including cancellation, and must preserve sibling and replacement backends. Core's package validator and a real runtime mount are separate attempts; a validator success alone never satisfies the runtime receipt.

Managed browser contexts are private per chat and lazily created. Ordinary web navigation is supported; the viewer streams the remote browser image rather than embedding websites directly. The user may interact to sign in. This does not supply managed-device SSO. Connected browser enrollment remains separately revocable; legacy exact-document grants do not imply navigation, screenshots or debugging access.

Observed native checkbox/radio controls include their checked state and native checkbox indeterminate state. ARIA checkbox/radio controls expose declared true/false state, with mixed supported for checkboxes and null for unknown state. These values participate in observation freshness. Caller success conditions can require multiple fields; every condition must match a unique visible control. Missing or mixed state cannot prove a boolean checked assertion. Invalid success conditions are rejected before input. The fixed executor and existing target grants remain authoritative.

This preview qualifies representative websites and desktop applications, not universal website compatibility. Protected browser pages, CAPTCHAs, browser permission dialogs, device-conditioned SSO and absent desktop executors produce explicit handoff. PWA screen sharing remains observation-only.
