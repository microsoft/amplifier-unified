# Voice transport

Calls use browser WebRTC for microphone/speaker audio and an authenticated server sideband for transcripts, app context, and Amplifier delegation. Set `OPENAI_API_KEY` in the terminal that launches the app. API keys stay on the Python host. A call remains pinned to the conversation that started it even when another conversation is selected in the interface.

`gpt-live-1` is the default preference and is tried first with the Live `/v1/live/sessions` JSON protocol and client delegation. Live delegation events contain metadata rather than request text. The host retains user transcript fragments, their timeline intervals and event identities, alongside pending delegation identities. A short bounded settling interval combines fragments and immediate corrections before admission; a delegation waiting for late transcription remains pending after its initial wait. Text is consumed only after durable backend acceptance. A timed fragment that arrives after its related request was accepted enters the same Amplifier conversation as an explicitly identified continuation, never as a replay of the original action. Approximate timestamps and a settling interval cannot establish a perfect semantic turn boundary; the backend still clarifies uncertain or unfinished requests before consequential actions.

Continuous trailing speech can follow an early delegation. The adapter groups whole fragments separated by at most 2.5 seconds on the provider timeline, within 20 seconds of the accepted input, and waits for 1.2 seconds of transcript quiet before submitting one supplemental batch. A new provider delegation takes priority over an unsubmitted batch. Once admission is attempted, its request identity and text remain immutable across retries. A continuation that exceeds the span or a 20-second quiet-wait limit requires restatement instead of submitting a partial request; fresh speech after quiet can start a new request. These are conservative heuristics, not guaranteed utterance boundaries.

Results return only from identified completed **root manager** generations. Child results and intermediate assistant content blocks do not complete requests or become manager narration. A result waiter timing out means the accepted work is still running; a later completed generation remains eligible for delivery. Realtime uses `/v1/realtime/calls` multipart signaling and its own function-call protocol with `gpt-realtime-2.1`. Its only function is `amplifier_delegate`. Reasoning, app inspection, controls, and work all enter the main AmplifierSession through loop-live; neither voice adapter executes app tools directly.

Selecting GPT-Realtime-2.1 as the saved preference connects directly to Realtime. Automatic fallback is limited to model/access availability errors. Invalid API credentials, rate limits, invalid configuration, and generic server failures are reported instead of concealed by trying another model. Reconnect to retry. There is no synthesized speech/transcription agent fallback in this version.

The host persists voice transcripts in the same conversation. Voice fragments are delivery fragments, not precise speaker turns. Unassigned transcript context has a five-minute, 512-fragment, 32-KiB retention budget; known pending and admission-retry input is retained intact. If idle context expires, a later affected delegation asks the user to restate the current request without submitting partial work. The complete transcript remains in chat. New Live calls seed bounded, role-labelled text history from both voice and chat. Oversized messages stay in canonical history, represented by an explicit availability notice. Both adapters receive a complete, bounded application-state summary as relevant state changes. Text added during a call produces a quiet receipt so the voice model knows it is already available to Amplifier. Full app state, repository access, shared canvas resources and controls remain behind the main Amplifier app tool and its normal orchestrator and approval boundary. The Live prompt describes conversation, interruptions and backend capabilities; detailed tool procedures remain with Amplifier.

Live appends remain below the documented 500-token limit using a conservative UTF-8 byte budget. Short verified answers return directly as commentary. Longer prose is sent as complete numbered factual units through thinking appends; only after every unit is acknowledged does a result-complete commentary invite Live to explain the full result, including its final qualifications. Indivisible oversized passages and code remain explicitly available in chat instead of being truncated into an incomplete claim. A rejected factual append blocks that completion announcement. Sent, context-acknowledged, rejected and uncertain delivery are distinct; an acknowledgment confirms estimated context injection, **not speech or playback**. A transport error does not relabel successfully completed Amplifier work as failed. After rejected or uncertain delivery, read the retained answer in chat or reconnect and ask for current status. No automatic injection retry or dedicated narration-only retry is provided; that recovery refinement remains open.

Accepted newer input advances the call's request revision. Older results that have not yet been sent as commentary become quiet reference context, preserving them without presenting them as the latest answer. Newly received user transcript also gates unsent result commentary while its request remains unresolved, before provider delegation or backend admission. The check includes transcript persistence, waiting on the append lock, and staged results finishing their acknowledgments. It does not advance canonical acceptance or cancel work. Live supplies approximate transcript timing rather than an authoritative speech-stop event; speech not yet transcribed and content already injected or audio already queued cannot be retracted by this mechanism. Interruption behavior and actual speech remain live-provider acceptance concerns. Quiet results remain reference context, without automatic delayed narration or execution replay.

Backend replies and actual voice transcripts retain separate provenance even when both originated from a call. Resume history labels known backend replies as reference results. A new backend submission repeats only the current request, concise voice policy, and at most four whole additional spoken messages within a 2,400-byte reference budget. User inputs confirmed in native history and backend replies are excluded. A prior attempt without native receipt, such as failed provider preparation, can remain labelled reference context for resolving the new request; it is not replayed. Oversized spoken messages become explicit availability notices, never truncated claims.

In the conversation view, verified backend outputs from voice requests live inside their matching **Working / Worked for** disclosure from the first streaming chunk onward. Exact input identity binds them to existing execution segments; this presentation does not create turns, change accounting, or infer completion. Expanded Work contains attributed Amplifier updates/results alongside its actions, with the original text and message controls. A link to a nested message opens its Work disclosure. If the owning execution is not loaded, a neutral **Work details** disclosure retains the backend content without inventing timing, usage or an owner. Streaming and its saved message retain the same disclosure choice. Spoken transcripts remain conversation replies. Unknown historical provenance remains an ordinary message; wording or an active call alone never establishes who produced it.

Spoken display bubbles use each speaker's provider timeline independently. When an opposite-speaker fragment falls wholly between two same-speaker fragments, the later fragment starts a new bubble; overlapping or late fragments can continue the existing bubble despite an intervening acknowledgment. Missing or invalid intervals fall back to observed speaker order. Accepted user input always starts a fresh display row for subsequent speech. This is approximate display grouping, not a semantic turn detector: Live provides fragment intervals but no completed-turn event or utterance ID. There are no word classifiers or added pause timers, and delegation ownership remains separate. See [OpenAI's transcript guidance](https://developers.openai.com/api/docs/guides/live-conversations#manage-speech-and-transcripts).

Live policy carries an acknowledged request forward after a clear “yes” or “sure” and asks for the requested answer directly, with less repeated acknowledgment. Its delegation policy uses the `Generate <|SpawnThinking|>` wording specified for `gpt-live-1` in [OpenAI's prompting guide](https://developers.openai.com/api/docs/guides/live-prompting). Prompting cannot guarantee actual wording or turn-taking; those remain live-call acceptance concerns.

While a known continuation is waiting for submission, an earlier result stays quiet and is qualified as answering only the accepted portion. If the addition is rejected or needs clarification, verified earlier facts remain narratable with an explicit qualification that the added work was not accepted and its backend-dependent facts remain unverified. Pending transcript alone does not advance the canonical accepted-input revision. The Live prompt also prohibits inventing missing facts from a partial backend reply.

Voice and backend policy carry unfinished explicit requests forward. A clear, authorized next step should be delegated or performed instead of becoming another offer to help or request to repeat the complaint. A genuinely uncertain transcript or missing user choice still requires clarification, and waiting for that choice must not be described as work already started. This addresses observed conversational stalls; prompt wording alone does not prove the model will follow the policy.

Named application controls such as Settings, Canvas and AI connections should be resolved by Amplifier, rather than asking the caller to define the interface terms. Clarification should wait for the rest of a still-arriving utterance. This is conversational policy, not an inferred speech-stop event: synthetic speech can be mistranscribed, and actual delegation and visible effects must still be measured.

Ending a call asks the provider to finalize, closes browser media, and leaves accepted Amplifier work running. A result arriving after hangup remains in the conversation without trying to speak through a closed connection. A false `finalized` flag means the call closed locally but final provider accounting was not confirmed. Closing the whole host process remains a separate application shutdown.

Live accounting starts with a pending receipt when provider session creation succeeds. Provider duration arrives separately in usage updates; the host never invents billed seconds from wall time. A sideband failure after creation settles that receipt as incomplete.

## Endpoints

- `GET /api/voice/config`: credential availability and model names, never credentials.
- `POST /api/voice/connect`: `{sdp, sessionId?, attemptId?, provider?: "auto"|"live"|"realtime"}` → `{id,attemptId,sdp,provider,model,sessionId,fallbackReason?}`. The bundled browser creates a fresh `attemptId` for each microphone setup.
- `POST /api/voice/ready`: `{id,attemptId?}` after media and the data channel connect, and after Live emits `session.started`. Both identities must match the active call.
- `POST /api/voice/end`: `{id?,attemptId?}` → `{closed,finalized,workContinues}`. At least one identity is required; delayed requests cannot end a replacement call. Explicit host-side `end()` remains a separate global operation.

All routes use the application's existing local authentication and origin checks. Browser `VoiceClient` takes the authenticated JSON `request` wrapper. Native microphone permission still belongs to the browser/operating system; agents can request a call but cannot grant that permission.

## Validation

### Mobile audio and interruptions

The browser requests `navigator.audioSession.type = "play-and-record"` where available for the duration of a call, restoring its previous audio mode on hangup or failed setup. Supported Media Session `togglemicrophone` and `hangup` controls use the same shared actions as the app buttons. System metadata shows only “Amplifier voice call”, without a chat title or transcript.

Audio-session and microphone interruptions are displayed without ending the call or changing the user's mute choice. Returning to the page or recovering audio retries playback on the existing audio element; it does not request another microphone stream, reconnect the provider, or replay messages. If playback requires a gesture, **Resume audio** retries it. A stopped microphone requires ending the call and starting again. Actual navigation away still ends browser media.

**Keep screen awake** remains an optional foreground fallback. Audio Session and Media Session provide audio integration and supported system controls, not permission to run indefinitely in the background. Screen lock, power saving, Bluetooth routing and incoming calls must be checked on physical devices. Installing a PWA alone does not establish that guarantee.

References: [Audio Session specification](https://www.w3.org/TR/audio-session/), [Chrome Media Session call-control sample](https://googlechrome.github.io/samples/media-session/video-conferencing.html).

Physical acceptance checklist (not yet executed): on iPhone Safari and its installed PWA, and Android Chrome and its installed PWA, disable the screen-awake fallback and test a locked screen through a quiet interval; then test Bluetooth car audio, an incoming-call interruption, a background/foreground transition, and battery-saving mode. Confirm both incoming audio and microphone capture, preserved mute, no duplicate transcript/delegation, and controls cleared after hangup.

Automated scenarios cover the delegation-only boundary, root-generation ownership, pending-worker status, coalesced-result deduplication, continued steering, late transcripts and corrections, rejected admission, late completion after a waiter deadline, append acknowledgment/rejection, final-caveat preservation, newer-input result revision, bounded resume history, typed-message availability, scoped call controls, and call/work lifetime separation. These fixtures make no paid API requests. Their assertions do not establish actual speech quality, account-specific model access, latency, or browser microphone/playback behavior; those require real-call acceptance.

A real synthetic resume scenario exposed a separate model-grounding failure: Amplifier inspected a saved canvas artifact, received `open:false`, and claimed it had reopened the artifact without dispatching an action. The browser correctly remained closed. The voice-to-backend prompt now requires an authorized action and verified outcome for mutation claims; inspection success alone is insufficient. This prompt policy is not a deterministic guarantee. Acceptance requires the same spoken request to produce an actual action receipt and visible browser state, not merely a plausible spoken answer.

## Call controls

Mute immediately disables the local microphone track; it does not cancel speech already playing or work already accepted. End call immediately silences the local microphone and speaker, then lets scoped provider finalization drain before releasing transports. The browser can send Live's documented `session.close` over the established data channel if host close is rejected or stalls. Failure to receive finalization before the bounded deadline is reported as incomplete. Application-state bookkeeping runs independently of the immediate local control. Each action carries its originating call or attempt identity, preventing delayed mute/end effects from changing a replacement call.

While the call’s conversation has active work, its call strip also offers **Stop work**, which invokes the shared conversation stop action for that conversation even after navigating to another chat. The call stays connected so the user can give another instruction. The control reports **Stopping work…** while cancellation settles. It does not undo completed actions or guarantee that an external operation already submitted can be recalled.
